# 架构对比：本项目 vs 指导论文

本文按**代码实际结构**与论文 **§III–§V** 对照。所有行号取自当前工作区，参数可配性经代码核实。

---

## 一、总体：论文 3 个概念层，项目 7 个实现层

**论文的架构只有三层：**

| 论文层次 | 内容 |
| --- | --- |
| ① 密码算法层 | DMAFE 的 9 个算法（§IV-A/B）+ NIZK 的 3 个算法（§IV-C） |
| ② 协议流程层 | 每轮的 4 个步骤（§V-A） |
| ③ 信任模型层 | w 边缘节点 / v 云 / n 客户端 + 两条门限 |

**论文没有**：网络协议、进程模型、状态管理、控制面、部署、前端。

**项目的实际分层：**

| 层 | 目录 | 规模 |
| --- | --- | ---: |
| 密码学核心 | `crypto/` | 4,020 行 Python + 1,817 行 Rust |
| 传输 | `transport/` | 1,405 行 |
| 角色服务 | `services/` | 1,686 行 |
| 实验编排 | `experiments/` | 1,705 行 |
| 训练 | `training/` | 627 行 |
| 验证策略 | `validation/` | 124 行 |
| 部署 | `deployment.py` + `topology.py` + `cli.py` | 964 行 |
| 前端 | `web/src/` | 3,606 行 |

**结论：论文描述的是"密码协议应该长什么样"，项目实现的是"一个能跑、能审计、能复现的系统"。** 两者不是同一层面的东西，逐项比较时必须分清"算法等价性"与"系统工程"。

## 二、逐层对照

### 层 1：密码学核心

| 论文 | 项目 | 关系 |
| --- | --- | --- |
| `GlobalSetup` / `AuthSetup` / `EKGen` / `VKGen` / `DKGen` / `Encrypt` / `VerDec` / `AggDec` / `AggComb` | `crypto/protocol.py`（1,263 行） | ✅ 公式级一致 |
| NIZK：batched Σ + 零知识平方和论证 + Fiat–Shamir，**一种** | `PROOF_SUITES = ('legacy','compact_range_v1','compact_norm_v1','lego_norm_v1')`，**四种可换** | 🟡 **架构不同** |
| CRS 只有 `Gen(1λ,L)→crs`，**无生成方式** | `crypto/lego_registry.py`（252 行）+ `runtime/proof-parameters/`（`pk.bin` / `vk.bin` / `manifest.json` / `installation.json`） | 🟡 **项目补上了可信设置** |
| 无 | `crypto/ipa.py`（210）Bulletproofs 内积论证、`crypto/compact.py`（313）聚合范围证明、`crypto/linkage.py`（76）共用 Σ 残差 | 🟡 项目自建 |
| 无 | `crypto/gpu.py`（879）+ `cuda_scheduler.py`（110）+ `gpu_profile.py`（85） | 🟡 项目自建 |
| 无 | Rust：`lib.rs` / `sigma.rs` / `lego.rs` / `linked.rs`（共 1,817 行） | 🟡 项目自建 |
| 关系 `R` **无范围约束** | 逐位范围证明 + 平方和范数 | 🟡 **项目更强** |
| `AggComb` 只查 `D` 相等 | `DGFL-AGGREGATE-PAIRING-V1` 配对象证明 | 🟡 **项目更强**（拜占庭聚合器） |

**最关键的一处**：论文的 NIZK 是**一个固定构造**，项目做成了**可替换组件**。这不是实现细节差异，而是架构层次的差异 —— 项目能在不改协议其余部分的前提下换证明系统。

### 层 2：传输（论文完全没有）

1,405 行，论文一个字都没写：

| 文件 | 行数 | 内容 |
| --- | ---: | --- |
| `binary.py` | 466 | 规范二进制编码（曲线点/标量原始字节、紧凑载荷） |
| `chunking.py` | 486 | 分块传输：绑定 task/round/epoch/清单摘要/块号/总数/整体摘要 |
| `security.py` | 307 | mTLS + Ed25519 签名 + X25519/HKDF + AES-GCM 密封信封 |
| `client.py` | 145 | RPC 客户端与重试 |

**论文只给算法，不给网络协议** —— 这是复现时最大的空白之一。

### 层 3：角色服务

论文把 `w` 个边缘节点的行为写成一个抽象角色。项目把它拆成 4 个真实服务：

| 角色 | 论文对应 | 项目实现 |
| --- | --- | --- |
| 客户端 | `S_i` | `roles.py` 的 `_train` |
| 边缘节点 | `A_τ` | `roles.py` 的 `_authority`（957 行中的主体） |
| 云服务器 | `R_t` | `roles.py` 的 `_partial` |
| **协调者** | **不存在** | `services/control.py`（444）+ `experiments/runner.py`（905） |

**"协调者"是项目独有的架构角色。** 论文的编排由边缘节点集体完成，没有独立控制面。

### 层 4：实验编排（论文没有）

`runner.py`（905）、`hardware.py`（396）、`telemetry.py`（196）、`resources.py`（104）、`evidence.py`（103）。

**论文的 §VI 是"报告实验结果"，不是"实现实验平台"。**

### 层 5：训练

| 论文 | 项目 |
| --- | --- |
| PFLlib 的 FedAvgCNN，582,026 / 878,538 参数 | `paper_models.py`（205）**定义了同样的 CNN**，但**未接入安全流程** |

### 层 6：验证策略

论文把筛选写进 §V-A 步骤 3 的叙述里。项目把它抽成独立策略模块 `validation/policy.py`（123 行），含可配的阈值与批次规则。

### 层 7：部署与控制面（论文没有）

`deployment.py`（714）、`topology.py`（73）、`cli.py`（177）。

## 四、仍然存在的实质架构差异

| # | 差异 | 性质 |
| --- | --- | --- |
| 1 | **CNN 未接入安全流程** | 能力缺口：`PaperCNN` 存在但 `runner`/`roles` **零引用** |
| 2 | **CIFAR-10 无数据通路** | 能力缺口：只有模型定义，无加载/下载/预处理 |
| 3 | **默认 `regroup` 而非不可变批次** | 安全取舍：缺少论文 MRPL 论证的结构前提；`fixed` 可恢复 |
| 4 | **无任务内动态加入** | 能力缺口：须结束任务、改部署、重启 |
| 5 | **训练配置入口受限** | `local_epochs ≤ 5`（论文用 10）、`rounds ≤ 20`（论文用 30） |
| 6 | **无完整安全论证** | 项目增加/更换了证明组合与状态约束，**尚未证明等价** |
| 7 | **coordinator 是控制面单点** | 论文未给控制面容错协议，无法认定论文更可靠 |
| 8 | **聚合完整性防护超出论文** | **项目更强**（论文定理 3 只覆盖 honest-but-curious） |
