# 使用过程中密码学体现不出来 —— 逐屏诊断与改造方案

日期：2026-10-12。方法：沿真实使用路径（部署 → 运行 → 验证 → 监控 → 对照 → 导出）逐屏核对前端与 API 实际暴露的密码学信息，并对到源码里真实存在但被丢弃的字段。

---

## 0. 结论

**这不是"密码学做得不够"，而是"密码学做完了，却在交给用户之前被丢掉了"。**

最能说明问题的一条：一轮完整的 DGFlow 结束，用户在界面上能看到的**唯一**密码学信号，是验证页表格里的一个徽章：

```
客户端     证明校验     验证评分      接纳决定      后端判定理由
client1   [通过]       0.92341      [接纳]       通过并纳入聚合
```

`通过` 或 `未通过`，就这两个词。而同一轮里实际发生的密码学有：

- 3 个边缘对 6 个客户端 × 650 坐标，各自生成两条（秘密 + 盲化）`s−1` 次多项式并做 Pedersen 承诺
- 24 个 G2 验证函数钥份额的密封与门限插值
- 6 份密文（各 31,200 B）+ 6 份证明（各 144,777 B）
- 6 次配对消掩码得到授权内积、6 次有界离散对数解码
- 4 份云部分解密各自带一个配对象证明，2-of-3 门限合并
- 2 次独立的有界离散对数（内积 + 650 个聚合坐标）

**用户一个都看不到。** 更糟的是：**这些字段大多已经在内存里、在 `result.json` 里、甚至在 `/api/status` 的响应里，只是没有任何界面元素去读它们。**

---

## 1. 逐屏核对：密码学在哪里被丢掉

### 1.1 部署页（`web/src/views/Deploy.vue`，846 行）

| 界面上有的 | 密码学含量 |
|---|---|
| 拓扑图（n/w/v、门限 s/e、归属连线） | 只表达"谁连谁"，不表达"谁持有什么钥" |
| 模式四选一 | **配置项，不是密码学** |
| 数据与运行环境、随机种子、样本上限 | 与密码无关 |
| **证明方案**（`Deploy.vue:627-629`） | ⚠️ 只有一个 `<option>`：`lego_norm_v1`。用户"选"了一个没有选择的选择 |
| **已安装的可信设置参数 CRS**（`:636-641`） | ⚠️ 唯一的密码学可见物，但呈现为 `650 维 / 8 位 / 7c094bd1ffdb…` |

**这是密码学最应该被看见的页面，实际只有两行哈希。**

而且拓扑图完全没有展示密码学分工：谁持有 DKG 份额、谁的验证函数钥被密封给谁、云的聚合钥怎么门限分片——这些是**唯一能体现"去中心化多授权方"的东西**，却一概没有。

### 1.2 运行过程中（`runner.py` 的 `event()`）

全部事件只有 9 处调用，密码学事件是**一行文字**：

```python
# runner.py:836
event('dkg','密钥节点共同建钥，核对同一公开转录',round_id)
# runner.py:869
event('training','客户端本地训练、量化；安全模式生成密文与范围/范数证明',round_id)
# runner.py:907
event('validation','归属密钥节点验证客户端证明；共享签名验证结果并按统一门限筛选成员',round_id)
# runner.py:968
event('aggregation', f"{len(approved)} 个客户端获准；等待至少 {e} 份聚合结果", round_id)
```

用户看到的是：

```
检查节点身份与双向 TLS 连接 ✓
密钥节点共同建钥，核对同一公开转录          ← 只有这一行，不知道建出了什么
客户端本地训练、量化；…生成密文与范围/范数证明   ← 不知道密文多大、证明多大
已收到 6 份客户端提交
归属密钥节点验证客户端证明；…              ← 不知道验的是什么
6 个客户端获准；等待至少 2 份聚合结果
第 1 轮完成，测试准确率 56.00%            ← 唯一有数字的一行，且与密码学无关
```

**运行过程中，密码学是"进度条"，不是"内容"。**

### 1.3 验证页（`Validation.vue`）

`validations` 行在源码里只有 5 个字段（`roles.py:620`）：

```python
{'client_id', 'proof_valid', 'score', 'decision', 'reason'}
```

**被丢弃、但当时就在手里的**（`roles.py:634-635`、`runner.py:1084`）：

| 字段 | 在哪产生 | 现在去哪了 |
|---|---|---|
| `packet_hashes[cid]` — 每份提交密文核心的 SHA-256 | `roles.py:635` | 进 `manifest` → 签名 → **界面不显示** |
| `manifest_hash` — 授权清单指纹 | `roles.py:640` | 签名 → **界面不显示** |
| `context_hash` — 全轮密码上下文指纹 | `roles.py:634` | **界面不显示** |
| `norm_squared` — 经证明绑定的公开平方范数 | `packets[cid]` | **界面不显示** |
| `reference_norm_squared` | `runner.py:1090` | 在 `result.json` 里 → **界面不显示** |
| `proof_hash` — 证明正文摘要 | `submission_core` | **界面不显示** |

界面只把这些压成了一个布尔值。**用户无法区分"证明真的验过了"和"这个布尔值恰好是 true"。**

### 1.4 监控页（`Monitor.vue`，12 行）

```vue
<template><TensorBoardPanel /></template>
```

原生 TensorBoard。所有协议指标都被映射成 scalar 曲线（`key_metric_tags` 约 55 个），**密码学操作本身不产生任何曲线**——没有密码文大小、没有证明大小、没有 pairing 次数、没有验签次数、没有门限插值。

用户看到的是"准确率上升、每轮 210 秒"——**和任何一个普通联邦学习项目一模一样**。

### 1.5 对照页（`Comparison.vue`）

比较的维度：**准确率、轮时、通信量、配置条件**。

于是出现最讽刺的一幕：

| 配置 | 准确率 | 轮时 | 通信量 |
|---|---|---|---|
| plain 明文 | 82.95% | **2.45 s** | **199 KB** |
| optimized 加密 | 82.95% | **637 s** | **914 MB** |

**准确率完全一样，加密版慢了 260 倍、多了 4600 倍通信量。**

对照页的呈现方式等于在告诉用户：**密码学是纯粹的负担，它什么都没带来。** 而这正是"用起来体现不出密码学"的最强形式——它不但不可见，它看起来还是负价值。

### 1.6 状态 API（`/api/status`）

**这里最可惜。** 节点健康响应**已经**返回了完整的密码学能力（`node.py:164-177`）：

```python
'capabilities': {
    'lego_norm_v1': available(),                     # ← 没用
    'aggregate_verification_native': ...,            # ← 没用
    'owned_validation': ...,                         # ← 只用于门控
    'batched_authorization': ...,                    # ← 没用
    'ciphertext_only_aggregation': ...,              # ← 没用
    'compact_aggregate_materials': ...,              # ← 没用
},
'native': loaded_native_evidence()                   # ← 完全没用
#   {'loaded_artifact_sha256': {…}, 'artifact_names': {...},
#    'evidence_scope': 'actual imported extension file hashes …'}
```

前端只用了其中三个（`Deploy.vue:261` 检查 `lego_norm_v1`、`deployment.js:21` 检查 `owned_validation`、`cloudStrategies.js` 检查 `cloud_strategies`）——**全部用于"阻止启动"，一次都没有用于"告诉用户现在跑的是什么密码学"。**

尤其是 `loaded_native_evidence()`：这是**当前进程实际加载的密码学原生扩展的 SHA-256**。这是整个系统里最有说服力的"密码学真的在跑"的证据，它已经躺在 API 响应里，**没有任何界面读它**。

## 2. 五个根因

1. **密码学被降级为"配置项"**：模式是下拉框、CRS 是哈希、证明方案是唯一选项。配置项是"启动前勾一下"的东西，用户不会把它和运行中发生的事联系起来。

2. **所有密码学证据被折叠成一个布尔值**：`proof_valid: true/false`。信息量为 1 bit。

3. **产出物没有"密码学身份"**：只有 `accuracy`、`duration`、`bytes` 这些 ML 指标。没有任何地方显示"这一轮的密文是 31,200 字节的 650 个 G1 点"、"这份证明的指纹是 xxx"。

4. **没有对照，就没有感知**：四种模式全带同一套外壳，差异只有筛选器。用户无法回答"如果去掉密码学会怎样"。

5. **演示动线从 ML 结果开始**：`demo-script.md` 和设计报告都先讲准确率。**密码学被讲成了背景技术，而不是主角。**

## 3. 改造方案（按性价比排序）

### A. 【最高优先级】把 `loaded_native_evidence()` 和节点密码学能力接到界面上

**成本：最小。收益：最大。** 数据已经在 API 响应里。

- 在**部署页拓扑图**上，点击任一节点弹出「节点密码学档案」：
  - 角色与归属（client所属authority）
  - `lego_norm_v1: true/false`
  - `owned_validation` / `batched_authorization` / `ciphertext_only_aggregation`
  - **`loaded_artifact_sha256`**（当前加载的原生扩展指纹）
  - 参与 DKG 时的份额数、门限值
- 在**系统状态条**加一个常驻指示：`BLS12-381 · arkworks · dgfl_native 0.2.0 · <指纹前12位>`

这一条单独就能把"界面里看不到密码学"解决掉一半。

### B. 【最高优先级】给每一轮生成一份「密码学收据」

新增一个面板（验证页顶部，或独立 tab），展示**该轮的密码学产出物链**：

| 产出物 | 可显示的字段 | 数据来源 |
|---|---|---|
| DKG 转录 | `transcript_hash`、参与边缘数/门限、承诺点数 | `Authority.transcript_hash` |
| 每客户端密文 | `ct` 字节数（650×48 B）、**G1 点前 2 个的规范编码前 16 hex**、`packet_hash` | `submission_core` |
| 每客户端证明 | 证明字节数、`proof_hash`、CRS 指纹 | `packet['proof']` |
| 每客户端公开范数 | `norm_squared`（经证明绑定） | `packets[cid]` |
| 授权内积 | 归属边缘解出的 `<x,z>` 与由此算出的余弦 | `validations[].score`（已有） |
| 授权清单 | `manifest_hash`、每份 `packet_hash`、边缘签名者列表 | `self.approval` |
| 云部分解密 | 每云 `D`/`E` 长度、`verification_hash`、云签名 | `partial_decrypt` 返回 |
| 门限合并 | 实际使用哪 2 个云、插值系数、恢复出的整数和 | `combine` |

**关键**：这些字段**绝大部分已经在 `result.json` 里或可在 `runner.py` 加几行就写进去**，不需要改任何密码代码。

### C. 【高优先级】对照页加"密码学代价"维度 + 一个「关掉密码学会怎样」实验

- 对照页在准确率/轮时/通信量之外，增加：**密文字节、证明字节、验证耗时、聚合耗时、配对次数**。
- 新增一个预设：**同数据、同种子、同 5 轮，plain vs dgflow 并排**，并明确标注：
  > "准确率相同（82.95%），但明文基线下主控能看到每个客户端的完整模型；加密模式下主控只见密文核心，且每份提交附 144,777 B 证明。"

**这直接把"密码学换来了什么"变成一张对比表。**

### D. 【高优先级】把"篡改实验"做成界面上的按钮

现在篡改只能作为实验**启动前**的攻击选项（`attack=tamper_proof`），用户看不到"改了什么、为什么被拒"。改成运行时验证面板：

四个按钮，各自显示**实际收到的拒绝原因**：

| 按钮 | 操作 | 预期反馈 |
|---|---|---|
| 篡改范数声明 | 对某客户端 `norm_squared + 1` | `证明未通过` → 具体关系式失败 |
| 交换密文 | 把 A 的密文配 B 的证明 | `上下文/客户端绑定不符` |
| 更换参考向量 | 用另一个 z 请求函数钥 | `only the fixed reference function is authorized`（`roles.py:799`） |
| 重放上一轮密文 | 旧 `round_id` 的密文 | 信封层 `envelope_context` 拒绝（`roles.py:294-305`） |

**这是让用户"感受到密码学在保护什么"的最直接方式**——保护只有在被攻击时才可见。

### E. 【中优先级】把密码学阶段变成监控页的一等公民

监控页现在只有 TensorBoard。建议：

- 在 TensorBoard 前面加一条**本轮密码学流水线**（可折叠）：
  ```
  DKG(2.95s) → EKGen/份额(288B×24) → Encrypt(0.12s, 31,200B) → Prove(?, 144,777B)
  → owner 验证(?) → VerDec(0.043s, <x,z>=-26) → 授权清单(manifest_hash=…)
  → 云部分解密(9.2s×3) → 门限合并(14.7s) → 下一轮模型
  ```
- 在 TensorBoard 指标白名单里加密码学组（`proof/` 分组已有 3 个 tag，但缺"证明字节数""密文字节数""配对调用次数""验签次数"）。

### F. 【中优先级】提供独立验证工具（证明不是"界面说通过了")

现在用户验证"证明真的有效"只能信任界面。加一个 CLI：

```powershell
dgflow verify-submission --runtime runtime --run <run_id> --client client1
```

它从 `result.json` 取出保存的密文核心、公开范数、CRS 指纹与证明，**用当前的公开验证代码独立重跑一遍验证**并打印每个关系式的通过情况。这才让"密码学可被用户自己验证"成立。

### G. 【中优先级】给模式起能体现密码学的名字

现在：`plain` / `encrypted` / `dgflow` / `optimized` —— 三个词都看不出密码学差别。

建议界面上改为：

| 现在 | 建议显示名 | 副标题 |
|---|---|---|
| plain | **无密码保护基线** | 主控可见每个客户端的完整模型；无证明、无筛选 |
| encrypted | **加密 + 范数证明** | 密文 + LegoGroth16 绑定平方范数；不执行异常筛选 |
| dgflow | **DGFlow 完整协议** | 上述 + 授权内积余弦筛选 + 固定批次 |
| optimized | **DGFlow（并行调度）** | 与上一项密码学完全相同，仅调度与传输优化 |

最后一行尤其重要——它明确告诉用户"这两个名字的密码学是一样的"，避免用户以为 `optimized` 是更强的密码学。

### H. 【演示动线改造】先密码学，后指标

现在 `demo-script.md` 的顺序是"展示正常完成的历史证据 → 启动加密任务 → 演示篡改证明"。建议改成：

1. **先打开节点密码学档案**：读出 `loaded_artifact_sha256`——"这是本机正在运行的真密码学扩展的指纹"。
2. **启动任务，停在 DKG 事件**：展示 `transcript_hash` 与 3 个边缘各自签名的同一转录。
3. **展示一份密文与证明的真实字节数与指纹**——不是"通过"，是"这是 31,200 字节的 650 个 G1 点，这是 144,777 字节的证明"。
4. **展示授权内积**：`<x,z>` 是密码学算出来的，不是客户端自报的。
5. **现场按四个篡改按钮**，逐个看到不同的拒绝原因。
6. **最后才给准确率与对照表**，并明确"密码学不改变精度（82.95% 相同），它改变的是**谁能看到什么**"。

---

## 4. 一句话总结

> 密码学在这个项目的使用过程中体现不出来，是因为它被**当成配置项**而不是**产物**。
>
> 用户需要看到的是：**密文有多大、证明的指纹是什么、函数钥密封给了谁、门限插值的系数是多少、篡改哪一位会被谁以什么理由拒绝**。这些数据几乎全都已经算出来了、甚至已经写进了 `result.json` 和 `/api/status` 的响应里，**只是没有任何界面去读它们**——最典型的例子是 `loaded_native_evidence()`，它握着"本机实际加载的密码学扩展指纹"这个最有说服力的证据，却连着三个版本无人问津。

**改造不需要碰任何密码代码，只需要让数据流到界面上。** 建议从 A（节点密码学档案）和 B（密码学收据）开始，这两项各是 1–2 天的工作量，能立刻改变"看不到密码学"的观感。
