# 提交文件与使用说明

交付目录中的文件用于组委会要求的三类材料，实际上传格式仍以比赛平台及附件模板为准。

| 类别 | 已提供材料 | 队伍提交时的操作 |
|---|---|---|
| 作品设计报告 | `design-report.pdf`，可编辑源文件在源码包的 `docs/submission/design-report.md` | 填入平台生成的作品编号；按官方附件模板复核格式；命名为“编号-2026密码竞赛复赛作品设计报告” |
| 相关支持材料 | `source.zip`：源码、测试、前端构建、实测记录、手册、图示、公开数据及对应离线依赖 | 按平台要求命名为“编号-2026密码竞赛复赛相关支持材料”；保留第三方许可说明 |
| 审批及签字页 | 不代填、不代签；需使用组委会附件 | 队伍按真实信息办理，并命名为“编号-2026密码竞赛审批及签字页” |

`manifest.json` 记录源码包及逐文件 SHA-256；`release-check.json` 记录对同一 ZIP 的离线重装验收。两者可与支持材料一起保存，便于确认文件未在传递中改变。设计报告和签字页按图片中的要求分别上传，不把签名页混入匿名报告。

报告保留“待填写竞赛平台生成编号”，不能用运行任务的 run_id 代替作品编号。自有报告、代码注释、截图与运行记录保持匿名；第三方公开文献及许可中的原作者归属不得删除或改成队伍原创。

## 队伍接手

先阅读 `README.md` 和部署说明，再按演示脚本复现至少一个完整加密任务。三位队员应分别能解释密码协议、训练与异常筛选、通信部署和证据记录，并交叉检查接口。设计报告明确区分论文借鉴、开源依赖和本作品实现；答辩稿提供代码追问准备，不应背诵超出已实现范围的能力。

随包的历史 JSON 是验收证据；新安装界面不会自动导入它。需要在新机器展示实时历史时，应创建并完成新的本地任务；此前的真实截图及原始记录可以作为已完成实验展示，并明确其来源。

本次交付范围是完整本机版本和三机部署手册。三台实体机器的内网地址、证书分发及现场联调由队伍按手册完成，不能把本机 12 进程记录改写成三机实测。
